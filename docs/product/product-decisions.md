## Approved Decisions to Preserve

- The proposed modular-monolith architecture, React/TypeScript, Java/Spring Boot, and PostgreSQL are approved. See `docs/technical/architecture.md`.
- MVP roles are `admin` and `guest`; guest voters do not sign in. Local POC self-registration, BCrypt credentials, dev-only HTTP Basic, one admin per church, and one church per admin are defined POC behavior.
- Board members are named for attendance but need no accounts; board membership/attendance must not connect a named person to ballot participation or choices.
- Nomination POC uses shared position-scoped links, admin closure, a committee-set per-intake name limit, and profile-local edits while intake is open. This does not establish a real-world submitter identity.
- Voting links do not expire and resolve to the authorized current session phase. Ballot selections require exact distinct-choice count; admin totals are live, viewer totals are controlled by Audience Presentation, and admin may close/reopen under the cutoff policy.
- A two-candidate, one-selection round with an even expected count `N` automatically closes after `N - 1` ballots; expected count is fixed at poll start. This may count profile/link submissions rather than verified people.
- Privacy promise is confidentiality from church users, not system operators or metadata correlation. Ballot choices must not be joined to voter identity in UI, audit, or church-facing reports.
- E1.1 lifecycle status contract approved 2026-10-21: `SETUP`, `IN_PROGRESS`, `COMPLETE`; draft alone is not progress; nomination intake, active/closed rounds, or current candidate decisions count as progress; the elected-opening count may continue as legacy election-progress semantics and can regress. It is superseded as the definition of position finalization by PD-020 (2026-11-07).
- E1.2 handoff records Product Owner approval and acceptance on 2026-10-21, with merge commit `a23033e`; verify target-branch provenance before treating this as confirmed completed dashboard status.
- **E6.10 (2026-10-23; voting visibility updated 2026-11-04 by PD-019):** One unexpired, revocable session-level bearer participant link resolves only its own current phase; one ballot is allowed per browser profile per poll, with its opaque association valid while that poll may be reopened/current and invalidated when superseded or the session ends. The admin sees live aggregate totals; Audience Presentation controls current aggregate visibility on participant and room viewer surfaces. Closing ends voting without a separate results reveal; reopening clears viewer totals until the control is enabled again. Historical reports remain out of scope for this session link.
- **PD-017 (2026-11-02, updated for voting results by PD-019 on 2026-11-04):** Open-intake names may be shown live on the room presentation only when the admin enables it. If the room is on at closure, the closed list is published to participants; otherwise post-close Show publishes to both. Hide retracts the list from both viewer surfaces. Successful poll start hides and clears prior content. During voting, the control may be re-enabled to show live aggregate totals on both viewer surfaces; close does not require separate results reveal. See E6.13/E4.7/E4.2/E6.8/E6.11 for implementation and API authorization/cache requirements.
- **PD-018 (2026-11-02, superseded in part 2026-11-07):** The original elected-outcome visibility and replacement wording is retained historically. See the 2026-11-07 addendum below for current finalization publication behavior and replacement selection rules; the top-eligible tie rule remains in force.
- **PD-020 (2026-11-07):** Persisted position lifecycle states are `In Progress`, `Finalized`, and `Reopened`. `Awaiting Acceptance`, `Ready to Finalize`, and `Vacancy` are derived conditions that determine available actions. An opening counts as filled only after an Elected candidate separately records Accepted; Elected is an immutable election decision, and Accepted/Declined are separate auditable response events. Finalization requires every opening Accepted and no open poll for that position, with explicit admin confirmation and an audit event. It ends participant activity for that position and presents a neutral completed-session state. Finalization does not publish names/results or change Presentation publication state: previously revealed and enabled content remains as-is, and existing explicit admin audience controls govern later show/hide. Finalized positions are read-only by default; polls, results, decisions, and audit remain accessible, and historical polls, ballots, results, and election decisions are immutable. Reopen is explicit, confirmed, and audited; it changes lifecycle and permits audited follow-up candidate response/decisions and new poll drafts, but does not create or activate a poll or mutate prior history. No voting rounds are created automatically. A post-finalization Vacancy follows PD-018; an admin chooses the replacement path and the application never automatically elects.
- **PD-018 replacement addendum (2026-11-07):** The base direct-invitation pool is candidates in the most recent completed, non-voided round associated with the opening's elected candidate. A direct invitee must have a saved `Advanced` decision in that round and must have no prior Accepted/Elected outcome for another filled opening, Declined response, or explicit Remove/Eliminated decision. Rank eligible candidates by aggregate vote count in that same round. A tie at the top cannot be resolved by arbitrary direct choice: create a fresh tie-break poll containing only the tied top eligible candidates, with admin confirmation. For a fresh replacement poll, the admin explicitly selects its roster from candidates in that same round, excluding candidates already accepted/elected for a filled opening, declined, or explicitly removed/eliminated, and records the roster rationale. Do not auto-elect or create rounds automatically; an invite must be accepted before its opening counts filled. If no eligible candidate remains or an invitee also declines, Vacancy remains derived and the admin must choose another allowed path or add approved candidates. Continued ranking/offer caps, automatic nomination, and committee process are not decided.
- **PD-018 publication addendum (2026-11-07):** Finalization neutralizes the participant session. Presentation publication is independent: retain only content previously explicitly revealed/enabled, and do not publish new names/results or clear prior Presentation content on finalization. Existing explicit admin audience controls govern subsequent show/hide. This supersedes PD-018's 2026-11-02 blanket statement that elected people appear on both current-session viewer surfaces for the finalization transition; see E6.8 and the position-finalization addendum in `docs/product/requirements.md`.
- **PD-019 (2026-11-04):** The authenticated admin sees live aggregate candidate totals during voting. The **Show audience presentation** switch governs aggregate-total visibility on both the participant link and room presentation; turning it off clears both. Closing ends ballot access and makes final totals available to the admin without a separate reveal action. After closure, the admin records exactly one action per candidate: **Elect**, **Advance**, or **Remove**. A valid decision set must elect at least one candidate or mark at least two candidates Advance. Until the set is valid and saved successfully, the admin remains on the current candidate-decision step and no draft is created. Saving creates a fresh draft from the Advance set with zero votes. Candidate decisions remain admin-only. Further UX/API validation details may be added in a later story; no separate story is created now.
