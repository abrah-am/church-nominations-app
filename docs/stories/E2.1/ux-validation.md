## Criterion Review

| Criterion | Source and automated evidence | Assessment |
| --- | --- | --- |
| Separate profile count from proposed-name-entry count, and avoid implying people count | Admin summary renders distinct labels and separate values. The profile explanation says browser profiles and explicitly says it is not a verified count of people; entry help says repeats are counted separately. `App.test.tsx` intake creation test asserts both labels and explanatory copy. | **Meets source/test review.** No identity attribution is rendered in the intake list. |
| Numbered, alphabetical, duplicate-preserving names | `normalizeNominationIntake` sorts full names with `localeCompare(... sensitivity: 'base')` and preserves original index for equal sort keys. Both open and closed views render an `ol`; `.intake-submitted-list` sets decimal markers and allows wrapping. The admin integration test checks `Jordan Lee`, `Sam Lee`, `sam lee` in order and confirms both case variants remain. | **Meets source/test review.** Test checks ordered item contents but does not assert visual marker appearance or stable ties with equal case-insensitive names. |
| Live announcements include counts and changed names, without submitter identities | `applySnapshot` announces profile and entry counts, plus added/removed names when names change; status uses `role="status"`, `aria-live="polite"`, and `aria-atomic="true"`. The stream test asserts updated counts and `Added: Morgan Diaz.` No profile/device identifiers are included. | **Meets source/test review.** Actual assistive-technology announcement behavior was not tested. The design asks to avoid noisy announcements; larger multi-name changes can produce a lengthy announcement. |
| Closure confirmation and post-close feedback | Admin displays a consequence-confirmation dialog with labelled title/description, focuses the safer `Keep intake open` action, traps Tab navigation, handles Escape, and restores focus to the trigger on dialog cleanup. On successful close, `focusClosedStatus` focuses `closedStatusRef`; the closed-status paragraph binds that ref and has `tabIndex="-1"`. `App.test.tsx` asserts dialog copy, initial safe-action focus, successful closed status, focus on the status paragraph, and preserved ordered list. | **Meets source/test review.** Escape, full focus containment, and focus return are source-inspected but not all directly tested. |
| Withdrawal confirmation and unsaved form behavior | Public page confirms removal of every saved name and presents `Keep my names` first. It focuses the safe action, traps Tab, handles Escape, returns focus to the trigger, and only clears all fields after successful withdrawal. Tests assert confirmation, success clearing both saved/edited fields, cancel preservation/focus return, and failure preservation without success messaging. | **Meets source/test review.** Backdrop click also cancels and leaves field values unchanged. Escape and full keyboard behavior were not directly exercised by the tests. |
| Public save behavior | Form supports complete-list replacement, named fields, count/limit, empty-field filtering, disables saving with no entered names, preserves local values on request failure, and announces confirmed success through `role="status"`. A save returning HTTP 410 switches to the closed state without claiming success. |
| Public submit label and count transitions | Primary action is `Submit names`, with `Submitting…` progress and submitted confirmation. | Focus handling | Global CSS provides `:focus-visible` outlines for buttons, links, and inputs; disclosure controls have visible focus rules. Source-level tab traps only enumerate the two dialog buttons; no browser check was made for all focusable descendants or assistive-technology semantics. |
| Closed versus unavailable public link | Public route maps 410 to a distinct `Nominations are closed` view and 404 to `This link is unavailable`, with separate copy. `App.test.tsx` verifies both headings. Closed public view has no editor or exposed submission list. | **Meets source/test review.** |
| Empty, loading, and error states | Admin has a loading status, open/closed empty states, alerts, and a stream fallback message. Its load-error state renders `Retry loading nominations` and withholds `Create intake`; the focused test simulates a network error, confirms the retry/no-create state, retries successfully, and confirms the loaded empty intake. Public load failure renders the `Could not load this form` heading, a `role="alert"`, and `Retry loading form`; the focused test retries and confirms the position form loads. ## Remaining Evidence Gap

- No required implementation UX fix was identified in the requested review. Responsive rendering, keyboard interaction in a browser, screen-reader behavior, and contrast remain unverified and should be completed before claiming full accessibility conformance.

## Limitations and Follow-Up Validation

- Checked the named source files, E2.1 UX design, and relevant `App.test.tsx` cases. Source inspection was static; no code was changed.
- The focused App test file passed 56/56 tests. Both load-error/retry paths and post-close focus are covered by assertions.
- No browser session, screenshot, responsive viewport check (including 320px), zoom/reflow check, keyboard-only browser run, screen-reader test, or color-contrast measurement was performed. Those outcomes are intentionally not claimed.
- Before full accessibility sign-off, perform rendered checks at narrow and desktop widths, keyboard/dialog interaction checks, screen-reader announcement review, and contrast measurement against WCAG 2.2 AA.

**UX disposition:** The three previously identified implementation findings are resolved and covered: public load failure is alerted/retryable, admin load failure does not offer intake creation and is retryable, and the closed-status paragraph is ref-bound/focusable with a passing focus assertion. No remaining required implementation UX fix was identified. Manual rendered/responsive/accessibility checks remain unperformed.
